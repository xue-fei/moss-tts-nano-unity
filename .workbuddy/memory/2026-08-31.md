# 2026-08-31 MOSS-TTS-Nano Unity 项目日志

## 主题：排查合成音频"中间有中断和奇怪语气音"

### 结论（关键）
C# 移植实现与 Python 参考实现在数值上等价，"中断"不是移植缺陷，是模型自身行为。

证据：
- greedy 模式（`--sample-mode greedy --do-sample 0`，完全确定性）下逐帧 token 全等：
  79 帧 × 17 通道，`first diff frame = None`、`total diff frames = 0`。
- 帧数 / 采样数 / 时长全等：79 帧 / 303360 样本/声道 / 6.32s。
- 分词全等：13 token `[8651,2691,11099,10670,7669,10364,4960,10986,10892,10621,10485,7306,10382]`。
- Python greedy 输出的中断比 C# 更严重：`dead=41 worst_run=39 worst_span=1.52s-4.64s`，
  即中间连续 3.1 秒静音。用户抱怨的那份 C# 输出只有 `dead=13 worst_run=6`。
- 静音段的 ch0 token 正是 `522/233/825/1002`，与 `SilentFrameGuard` 注释里记录的静音 token 集合
  `{61,233,522,825,980,1002}` 吻合 —— 说明模型确实在自己吐静音 token。

### 中断的实际规避手段（已实测）
seed 扫描（Junhao，fixed 模式，12 个 seed）：`worst_run` 从 4 到 24 跨度极大。
- 最好：seed=4（`dead=6 worst_run=4`）、seed=2（`worst_run=5`）
- 最差：seed=7（`worst_run=24`，等于 1.9 秒空白）、seed=9（21）
音色扫描（seed 3/4）：Xiaoyu / Yuewen / Zhiming 普遍优于 Lingyu（`worst_run=11~14`）。
最佳组合：Xiaoyu seed=4（`worst_run=3`）、Yuewen seed=3（`dead=4`）。

所以「换 seed」是零成本的最优解，「换音色」次之。
`CollapseDegenerateSilence` 会丢帧改时间轴、削掉正常句读停顿，原版 Python 没有此逻辑，保持默认 false。

## 主题二：CUDA 加速接线（此前完全没生效）

### 发现的 bug
`ExecutionProvider` 参数从 `MossTtsComponent`（默认值就是 `"cuda"`）一路传到
`OrtCpuRuntime._executionProvider`，然后**就断了**。
`OnnxRuntimeEngine.CreateSessionOptions(int threadCount)` 从来没接收过这个参数，
只设 `GraphOptimizationLevel / ExecutionMode / IntraOpNumThreads`，
从不调用 `AppendExecutionProvider_CUDA`。
所以此前所有推理（包括 Unity 里跑的）**全部是纯 CPU**，
Inspector 上写着 cuda 只是个没人读的字符串。

### 修复
- `IInferenceEngine`：`InitializeSessions(int threadCount, string executionProvider)`，
  新增 `string ActiveExecutionProvider { get; }`。
- `OnnxRuntimeEngine`：`CreateSessionOptions` 接收 EP，请求 cuda 时
  `options.AppendExecutionProvider_CUDA(0)`，try/catch 失败则打 warning 回退 CPU
  并把 `ActiveExecutionProvider` 置为 "cpu"。CUDA EP 排在 CPU 之前，未覆盖算子由 CPU 兜底。
- `OrtCpuRuntime`：传 `_executionProvider` 进去，之后用 `_engine.ActiveExecutionProvider`
  回写自己的字段（避免显示"请求值"而非"生效值"），并暴露 `ActiveExecutionProvider`。
- `MossTtsService`：暴露 `ActiveExecutionProvider`，日志带 `(EP=...)`。
- `MossTtsComponent.LoadModel`：请求值 ≠ 生效值时打 warning。
- `Tools/MossTtsCliCheck`：新增 `--ep cpu|cuda`，输出
  `execution_provider_requested` / `execution_provider_active` 两行。

### 实测收益（GTX 1070，"欢迎关注模思智能..." 48 帧 / 3.84s 音频）
| EP | elapsed | 说明 |
|---|---|---|
| cpu | 4.04s / 4.33s | 4 线程 intra-op |
| cuda | 2.71s / 2.77s | 约 1.5x |

输出音频**逐帧能量完全一致**（`dead=6 worst_run=4 worst_span=2.40s-2.72s` 两侧相同），
但 md5 不同（GPU 浮点累加顺序不同，属正常）。
加速比只有 1.5x 的原因：ORT 报了 12/16/24/24/36 个 Memcpy 节点插入，
说明图被 CPU/GPU 来回切分；且模型是 100M 的自回归逐帧解码，
每帧 kernel 太小、GPU 利用率低，PCIe 往返占了大头。

### 离线校验工具跑 CUDA 的坑
`MossTtsCliCheck` 用 NuGet `Microsoft.ML.OnnxRuntime 1.20.1`，
带的是**纯 CPU 版** onnxruntime.dll，不导出
`OrtSessionOptionsAppendExecutionProvider_CUDA` → 报
"Unable to find an entry point named ... in DLL 'onnxruntime'"。
Unity 侧真正的 GPU 库来自 `Packages/manifest.json` 的
`onnxruntime-cuda`（github.com/xue-fei/onnxruntime-unity-cuda），
落在 `Library/PackageCache/onnxruntime-cuda@*/Plugins/Win/`：
`onnxruntime.dll`(12MB, ORT 1.22.1) + `onnxruntime_providers_cuda.dll`(322MB) +
`onnxruntime_providers_shared.dll` + tensorrt。

解决：新建 `Tools/setup_cuda_probe.sh`，把这三个 dll 拷进
`Tools/MossTtsCliCheck/bin/Debug/net8.0/runtimes/win-x64/native/`。
**每次 `dotnet build` 都会被 NuGet 的 CPU 版覆盖回去，需要重跑脚本。**

运行时还必须把 CUDA/cuDNN 放进 PATH：
```
export PATH="/c/Program Files/cudnn-windows-x86_64-9.0.0.312_cuda12-archive/bin:/c/Program Files/NVIDIA GPU Computing Toolkit/CUDA/v12.8/bin:$PATH"
```
本机环境：GTX 1070 8GB / driver 582.66 / CUDA 12.8 / cuDNN 9.0.0.312（装在
`C:\Program Files\cudnn-windows-x86_64-9.0.0.312_cuda12-archive\bin`，不在默认 CUDA 目录下）。
Unity 版本 2021.3.21f1，托管 API 用 `ORT_API_VERSION = 14`。

## 直接加载 tokenizer.model（已完成，0 error）

上一轮遗留问题：`tokenizer_sp.json` 找不到，回退到 `SimpleUnicodeTokenizer`，
直接把汉字转成 Unicode 码点（27426, 36814...），模型收到完全错误的 token 序列。

**根因**：`OnnxTtsRuntime.InitializeTokenizer` 只找 `tokenizer_sp.json`，
需要跑 `MOSS-TTS-Nano/export_tokenizer_assets.py` 从 `tokenizer.model` 预导出。

**修复**：新增 `Assets/Scripts/MossTtsNano/SentencePieceModel.cs`，
直接解析 `tokenizer.model` 的二进制 protobuf（ModelProto 三层：pieces/trainer_spec/normalizer_spec），
提取 pieces/scores/types、byte_fallback、unk_id/bos_id/eos_id/pad_id、
precompiled_charsmap（237561 字节的 nmt_nfkc 归一化规则表）。

`SentencePieceTokenizer` 新增 `public SentencePieceTokenizer(byte[] modelBytes)` 重载，
`InitializeTokenizer` 改为优先加载 `tokenizer.model`，回退到 `tokenizer_sp.json`，
最后才回退到 `SimpleUnicodeTokenizer`。

**验证**：Python 解析 tokenizer.model 确认 16384 pieces、model_type=2 (BPE)、
byte_fallback=true、unk_id=1、bos_id=2、eos_id=3、normalizer=nmt_nfkc、
precompiled_charsmap=237561 字节。C# 编译 **0 error**。

**关键 protobuf 结构**：
- field 1 (repeated SentencePiece): piece(string) + score(float32) + type(varint)
- field 2 (TrainerSpec): model_type=2, byte_fallback=field 19, unk/bos/eos/pad_id=field 41-44
- field 3 (NormalizerSpec): name=field 1, precompiled_charsmap=field 2, add_dummy_prefix=field 3

`SentencePieceModel.cs` 需手动加进 `Assembly-CSharp.csproj`（同 ModelPaths.cs 的老问题），已加。
